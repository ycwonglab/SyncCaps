# SyncCaps — experiment package

Code, configurations, per-seed results, prediction dumps, statistics and figure
provenance for the SyncCaps manuscript (UCF101 / UCF-11 activity recognition
with a pairwise-synchronisation capsule readout).

This repository is the **integrity bundle**: everything needed to check a
reported number without retraining, and everything needed to retrain it if you
want to. It contains no dataset video files, no credentials and no private
paths.

---

## What the method is, in one paragraph

A frozen image backbone produces per-frame features. Those are projected to a
3×3 capsule grid (`PrimaryCaps(256, 32, 8)` → `d_model = 2304`) and read out by
`PairwiseSync`: a fixed dictionary of `n_synch` neuron pairs `(i, j)` whose
products are accumulated across the 16 ticks of a clip under a learned per-pair
exponential decay `r = exp(−ρ)`. The accumulated vector, optionally
signed-sqrt + L2 normalised (`sync_norm`, improved B-CNN), is the classifier's
only input. The arms below isolate each piece of that description.

| arm | what it is | what it isolates |
|---|---|---|
| `B0_linear` | per-frame linear readout, no sync | the backbone alone |
| `B1_sync` | pairwise sync, learned decay, no normalisation | the raw sync statistic |
| `B4_syncnorm` | `B1_sync` + signed-sqrt + L2 | second-order **pooling** |
| `B4_gram` | `B4_syncnorm` with `ρ` frozen at 0 (`r = 1`) | whether the decay buys anything |
| `B3_shuffle` | `B1_sync` on frame-shuffled clips | temporal **order** |
| `CB_tsketch` | Count-Sketch (Pham & Pagh) at equal head width | exact pairs vs sketched |
| `LR_bilinear` | low-rank bilinear pooling | a third pooling scheme |
| `R3_route` | 3-iteration dynamic routing | routing vs sync, same stem |

`B0`, `B1`, `B4` and `B3` share the stem, the tick loop and the head width, so
each difference is attributable to one factor.

## Layout

```
src/            model, training, evaluation and profiling code
configs/        one JSON per reported experiment (55), grouped by family
splits/         materialised train/val/test partitions + SHA-256
pair_indices/   the exact pair dictionaries and Count-Sketch hashes + SHA-256
results/
  seed_summaries/   seed-level CSV (189 runs) + the raw committed JSON
  predictions/      per-clip prediction dumps with clip and source-video ids
  statistics/       McNemar / bootstrap / TOST outputs, unedited
  timing/           latency profiles including the raw 100 measurements
checkpoints/    manifest + SHA-256 (weights ship as Release assets)
figures/        plot scripts, inputs, rendered figures, provenance manifest
provenance/     the generator scripts and the claim → evidence map
reproduce/      entry points for tables, figures and statistics
environment/    system record and dependency lock
```

Every file under `splits/`, `pair_indices/`, `results/predictions/`,
`results/statistics/` and `checkpoints/` was **generated by a script in
`provenance/` or `src/evaluation/`**, not written by hand. Re-running those
scripts regenerates them byte-for-byte.

### 55 configs but 60 manifest rows

`configs/` holds **55** files, one per unique `experiment_id`, while
`provenance/experiment_manifest.csv` has **60** rows. The difference is real,
not an inconsistency: five experiment IDs were run in **two seed batches**
recorded in two different results files. Each batch is one manifest row; the
config merges both and lists the union of seeds. `result_batch_id` appears in
both `experiment_manifest.csv` and the seed-level CSV so joins are unambiguous,
and each config carries a `seed_batches` array naming the source file per batch.

This is how the nine-seed exact-vs-sketch comparison is assembled: seeds
`7,42,1337` from one batch and `5,11,19,23,101,2026` from another.

### The code that produced the results

`main` carries the code **repackaged** into `src/`. The bytes that actually ran
are on the **`experiment-source`** branch — the recorded commit is *not* the
experiment source, and re-running it would reproduce a retired leaky split. See
`environment/system-info.txt` and that branch's README. To check the
repackaging:

```bash
git worktree add ../expsrc experiment-source
PYTHONPATH=. python provenance/verify_source_equivalence.py --snapshot ../expsrc
```

## Reading the results table

`results/seed_summaries/seed_level_results.csv` has one row per (experiment,
seed) — 189 rows. Three accuracy columns matter and they are **not**
interchangeable:

| column | policy | causal? |
|---|---|---|
| `*_acc_certain` | argmax over all 16 ticks by certainty | **no** |
| `*_acc_final` | logits at the final tick | yes |
| `*_acc_hybrid` | prefix-mean logits, exit at θ = 0.5 | yes |

`mean_exit_tick` is defined **only** under the hybrid policy. Never pair an
exit-tick number with a `certain` accuracy — they come from different readouts.

`three_clip_*` columns are the 3-view re-score. `single_view_drift` is the gap
between the re-scored and the originally logged single-view accuracy; it is
`0.0` everywhere except the two `B3_shuffle` rows, where it is `0.02643` —
exactly **one clip in 3783**. `B3_shuffle` is the only arm that consumes RNG
inside its forward pass (to permute frames), so re-scoring it under a different
RNG stream can flip one borderline clip. No other arm is affected.

## Protocol notes that change how numbers compare

**Two split protocols exist and must never be mixed in one table.**
`official1*` is UCF101's published split-1 (test = source groups g01–g07); the
reconstruction is checked against the official lists and matches exactly —
9537 train / 3783 test. `seeded_seed<N>` is a group-disjoint
`StratifiedGroupKFold`. Both are leak-free but they are *different partitions*.

**`_noval` means no validation set.** Training uses all 9537 official train
clips, as published methods do, and the **final** epoch is kept rather than a
best-val checkpoint. Experiments without `_noval` select on validation
accuracy. The `epoch_selection` column records which rule applied.

**`_fc` means the frozen-BatchNorm correction is applied.** Before 2026-08-21,
frozen stems still ran their BatchNorm in training mode, normalising with
per-batch statistics at batch size 4 and mutating running stats. Every
experiment id containing `_fc` is post-correction; ids without it are
superseded and are retained only for the record. `src/models/sync_caps.py`
now asserts this on every `.train()` call, so the defect cannot recur silently.

**Group-aware splitting matters a lot here.** An earlier clip-level split leaked
clips of the same source video across train and test. Numbers from that era are
not in this bundle.

## What `reproduce_statistics.sh` does and does not cover

It runs three analyses, all from released artifacts and none needing a dataset,
a GPU or a checkpoint:

| analysis | script | covers |
|---|---|---|
| seed-level contrasts | `synccaps_repair_report.py` | exact-vs-sketch (9 seeds, fresh seeds, CLIP, and the backbone × operator interaction), routing operational band with TOST, zero-decay, pair composition, val-carved replication |
| clip & group inference | `synccaps_mcnemar.py` | McNemar, clip-level and source-video-clustered bootstrap, TOST, Bonferroni family |
| remaining claims | `synccaps_claim_analyses.py` | frame-permutation disagreement, head-parameter and latency ratios |

`provenance/claim_evidence_map.csv` maps every manuscript claim to the exact
analysis, raw file, config and support artifact behind it, with the statistic
recomputed rather than transcribed.

## Known gaps

Stated plainly rather than omitted:

- **Per-tick logits, exit ticks and certainty values are not in the prediction
  dumps.** `synccaps_perclip_dump.py` persisted only the three per-clip
  prediction vectors, the labels and the test indices. Clip and source-video ids
  were recovered exactly (see `provenance/build_predictions.py`), which is
  enough for the McNemar tests and the clustered bootstrap; per-tick tensors
  would need a re-run from the released checkpoints.
- **`results/timing/readout_profile_replication.json` is ~4× slower in absolute
  terms than the published profile.** The replication ran against a GPU already
  at 98% utilisation from another process, with SM clocks held at 2535/3105 MHz;
  the file records that state in `_meta.gpu_state_before`. Parameter counts and
  peak activation memory match the published run exactly, so the graphs are
  identical — only the wall-clock is contended. Re-run on an idle device to
  reproduce the published 5.64 / 6.88 ms and 10.03 / 12.21 ms.
- **`results/seed_summaries/legacy_no_config/`** holds conv4 and probe results
  that predate the `_config` convention. No config files were synthesised for
  them, because their hyperparameters are not recorded in the artifact and
  reconstructing them from filenames would be a guess.
